# SU2 report — cruise simulator page: time charts, settings, batch views, report view

2026-11-19 · agent SU2 · branch `cruise-sim/su2` (worktree `.claude/worktrees/cs-su2`) · not pushed, not merged.

## What was built

All under `tools/cruise-sim/`. Plain JavaScript, no library, no network, no build step; canvas and SVG drawn by our own code; light and dark; a colourblind-safe palette. Each file registers `self.CS.<name>` in the browser and `module.exports` under Node, and has `mount(el, app) -> { destroy() }`. The views talk to the shell only through `app` (CONTRACT.md "The page"), plus what SU1's shell offers additively: `setCursor`, `setCompare` / `resultB` / `'compare'`, `openRun`, `showView`, `isShort`, `autoRun`, `'view'`, `'batch'` / `app.batch`.

| File | Mounts into | What it does |
| --- | --- | --- |
| `ui/charts.js` | `#charts` | Time charts linked to the scrubber: speeds (ours, lead true / estimated, set speed commanded / held, driver maximum, v_ref off by default), gap (true, measured samples, estimated, desired, needed), time gap with the pass threshold and target h, TTC with the pass threshold and TTC_warn (capped at 20 s, the axis says "≥ 20"), accelerations with the plant's a_min / a_max, the event lane (commands sent / applied / dropped / rejected, target, warning spans, driver, cruise state, fault spans, collision). Warning periods shaded on every panel, collisions as red lines. Zoom on the wheel (about the pointer), pan with shift-wheel or horizontal scroll, shift-drag zooms to a range, double-click = whole run, click / drag moves the shell's cursor, "Follow cursor" during playback, legend items hide series, tooltip with the values of A (and B) at the pointer. A / B: "Pin as B", "Load B…", "Baseline as B" (ideal ACC or human driver on the same config), a metrics table A vs B. Min/max (M4) decimation per pixel column, so a 30-minute run draws as fast as a short one. Also the shared pieces: palette and theme CSS, scales, ticks, draw ops rendered to canvas or to an SVG string (the report uses the SVG). |
| `ui/settings.js` | `#settings` | Generated from every module's SCHEMA (nothing about a parameter is written in this file). Groups: scenario (catalogue by family, then its concrete variant, seed, duration, ego mode, recorded step) · plant (preset, model, every parameter, "Load identified plant…" writes `plant.data`) · sensor · estimator · controller and warning · command path (its PRESETS as a selector that only writes values) · driver · failures (a list editor; kinds from `failures.KINDS`, `at` accepts "worst") · baselines (SC2's SCHEMA, stored in `ego.params`) · pass thresholds. Each control: unit, default, range, slider where the range is finite, km/h hint for m/s values, a changed mark (against the selected preset, not just the SCHEMA), a range error shown in place. "Reset group" per group, a search box, named presets saved in the browser / exported / imported as JSON (unknown keys and out-of-range values dropped with a warning; a bare config file imports as one preset). Re-run on change for short runs (delegated to the shell's `isShort` / `autoRun`), otherwise "changed since the last run" and the Run button. |
| `ui/batch.js` | `#batch` | Reads `sweep.js`'s `batch.json` (SC3) and tolerates other shapes. **Scenario matrix**: per parameter set (grid point; presets first), families → scenario rows → variant cells, ✓ / ✗ with the deciding metric (the failed one, else the one closest to its threshold), dashed = warn-only / out of envelope; a click opens exactly that run in the scene (base + grid point + the variant's config patch, scenario by concrete id). **Feasibility map**: sweep.js's own `summary.maps` (all grid points, per family too), or any two swept parameters from the runs with pass share or any metric (worst / mean / min / max); cells binned when there are many values; plant presets marked; a frontier line where the cell reaches a target. **Sensitivity**: tornado at −30 % / +30 % (from the runs, with per-variant verdict changes counted, or from `summary.tornado`), choosable measure. **Tuning sweep**: sets ranked by pass share, then a comfort cost (each comfort metric over its threshold), Pareto stars; a row click applies its parameters. Small batches also run in the page (main thread in 40 ms slices, progress, cancel): "Run matrix here", "Run map here", "Run ±30 % here". |
| `ui/report-view.js` | `#report` | `buildReport(data)`: one self-contained HTML page (inline CSS and SVG, no script, light and dark): the plant and whether it is assumed (an assumed plant is never worded as a verdict), a summary in English and Ukrainian, "measure this first on the car, because the verdict turns on it" (ranked from the tornado, else sweep.js's ranking, else the parent brief's order; each with the car measurement in both languages), the current run's metrics against the thresholds and its charts, the matrix, the maps, the tornado, the best tuning sets, the worst cases, the changed settings and the whole config. The page view previews it and downloads it (`cruise-sim-report-YYYYMMDD-HHMM.html`; the browser cannot write into `bake/work/cruise-sim/reports/`, the owner saves it there). Pure and Node-loadable, so SC3's `report.js` can produce the same file. |

## How the owner checks each view by eye

Open `tools/cruise-sim/ui/index.html` from the disk after the merge (SU1's page). Without the merge, `tools/cruise-sim/tests/stubs/su2-dev.html` shows the four views on a fake shell (real core files are used when present). Try both themes (OS setting, or the shell's toggle; the dev page has "Theme").

1. **Charts** (Run view): run `D.brake`. Six panels; the shaded bands are the warning; the TTC panel has a red dashed "pass ≥ 4 s" and a dotted "warn < 3 s"; the acceleration panel has the plant's grey a_min / a_max lines. Play: the black cursor line moves on every panel and the window follows it. Wheel over a chart: it zooms about the pointer; shift-wheel pans; shift-drag zooms to the dragged range; double-click returns to the whole run. Hover: the tooltip lists every visible series at that time. Click "Ego" in the speeds legend: it disappears (strike-through). "Pin as B", change a setting, run: B is drawn faint under A and "Metrics, A against B" appears below. "Baseline as B" with "ideal ACC": the ideal adaptive cruise is overlaid.
2. **Settings**: every group opens; values show unit, default and range; change "Max deceleration" in Plant → the row gets an amber bar and "1 changed", and (short run) the charts update by themselves; type 0 → a red message, nothing changes; "Reset group" clears it but keeps the preset; switch the preset to "firm" → the parameters move to firm's values without a changed mark. Pick a scenario, then a variant ("v=90,dv=40,a=-1 · …"). Command path → Preset "worst". Failures → "+ Add a failure", set "at" to `worst`. Presets → Save as…, change something, Apply → it comes back; Export, Import the file again.
3. **Batch views**: run `node tools/cruise-sim/sweep.js <plan.json>` and load its `batch.json` ("Load batch file…" or the shell's Open file). Matrix: blue ✓ / orange ✗ cells with the deciding metric; pick another parameter set at the top; click a cell → the scene opens that exact run. Feasibility map: the diamonds are liftoff / mild / firm; choose "family D"; set "frontier at" 0.8 → a black line separates the cells that reach 80 %. Sensitivity: bars sorted by effect, ⚑n where verdicts change. Tuning: ★ rows; click one → its parameters land in Settings. "Run matrix here" runs the catalogue in the page with a progress bar and Cancel.
4. **Report**: "Build report" → the preview shows the banner "Assumed plant: … not a verdict", the English and Ukrainian summaries, the measure-first list, the run, the matrix, the maps; "Download HTML" saves it; open the file on its own (no network, both themes).

## Decisions made here (the owner may overrule)

- **Colours**: the dataviz reference palette in its validated CVD order; colour follows the entity (ours blue, the lead orange, the controller aqua, the cruise green, the estimator violet, the warning red, the car behind magenta); measured = dots, estimated = dashed. **Pass / fail are blue / orange with ✓ / ✗**, not green / red (red-green is the most common colour blindness). The heat map is one blue ramp, darker = better, with the value printed in each cell.
- **Settings write compact modules** (only what differs from the defaults of the selected preset) and replace the config (`setConfig(next, { replace: true })`), so links stay short and a key can be removed. The command path's PRESETS have no `preset` key in its SCHEMA, so selecting one writes its values only (the engine would reject an unknown key).
- **A scenario variant is its concrete id** (`D.brake#v=90,dv=20,a=-1/none`), plus the variant's own config patch; `scenario.overrides` is not used (the engine deep-merges it onto the scenario object, so sweep paths in it did nothing).
- **In-page batches run on the main thread in slices**, not in a worker: `worker.js` is SU1's. Fine for a few hundred runs (~12 ms each); larger ones belong to `sweep.js`.
- **A batch file without series** (sweep.js's) gives worst cases without charts in the report; the page opens any of them from the matrix.

## Left out, and why

- Y-axis zoom per panel (x is zoomed and linked across panels; y fits the visible data).
- A worker for in-page batches (SU1's file; see above).
- Charts of the worst cases inside the report when the batch has no series: SC3's `report.js` could re-run them with `CS.batch.runConfig(run, batch)` (exact, see above) and pass their results in.
- The cluster preview hook of §4.1 is SU1's.
